ID: T-007
Цель: Проверить и закрепить поведение backend при незаданных SECRET_KEY и ENCRYPTION_KEY, зафиксировать, как устроен redirect_uri. Задача сужена: Google OAuth в контейнерах уже работает.

Контекст:
- Среда: Windows, PowerShell (без `&&`, `export`, `grep`; для поиска `Select-String`).
- Всё приложение запущено через docker compose и работает: вход, ЭИОС, Google-авторизация, экспорт в календарь, аналитика. `GOOGLE_REDIRECT_URI` в контейнерах равен `http://localhost:8080/google-callback`, при разработке на хосте `http://localhost:5173/google-callback` (маршрут фронтенда `/google-callback`, он читает `code` и делает POST `/auth/google/callback`).
- `GOOGLE_REDIRECT_URI` читается в `backend/app/routers/google_auth.py:17-20`, `SECRET_KEY` в `backend/app/auth_utils.py:10-15`, `ENCRYPTION_KEY` в `backend/app/core/security.py:17-29`. Пароль ЭИОС хранится в БД в зашифрованном виде.
- Риск: если ключа в env нет и код генерирует случайный или берёт дефолт, то при каждом старте контейнера ключ другой. Зашифрованные в БД данные после рестарта нечитаемы, а при чистом клоне без `.env` приложение молча стартует с небезопасным ключом.

Файлы (читать можно любые, менять не более 2):
- `backend/app/core/security.py`
- `backend/app/auth_utils.py`

Делать:
1. Описать в ответе, что делает код при незаданных `SECRET_KEY` и `ENCRYPTION_KEY` (дефолт, генерация, ошибка), с файлом и строкой.
2. Если дефолт или генерация: заменить на `raise RuntimeError("<ИМЯ> is not set")` при импорте. Если уже падает с понятным сообщением, не менять ничего.
3. Описать в ответе, откуда берётся значение `GOOGLE_REDIRECT_URI` по умолчанию в `google_auth.py:17-20` и используется ли оно и в ссылке авторизации, и при обмене кода. Если дефолт указывает не на `/google-callback`, не менять, только сообщить.

Не трогать: `google_auth.py`, алгоритм шифрования, JWT, модели, CORS, фронтенд, Docker-файлы.

Готово, когда:
- в ответе есть описание поведения по п.1 и п.3 (файл:строка);
- без `SECRET_KEY`/`ENCRYPTION_KEY` backend не стартует и называет переменную;
- с заданными ключами всё работает как раньше, после пересборки образа (`docker compose up --build -d backend`) и перезапуска данные читаются;
- дифф ≤2 файлов (или пустой, если менять нечего).

Как проверить:
```
docker compose up --build -d backend
docker compose run --rm -e ENCRYPTION_KEY= backend
docker compose run --rm -e SECRET_KEY= backend
docker compose restart backend
```
Код копируется в образ при сборке, поэтому без `up --build` изменения не применятся. Вторая и третья команды должны завершиться ошибкой с именем переменной. После `restart` открыть расписание из ЭИОС (расшифровка сохранённого пароля).

Формат ответа: описание по п.1 и п.3 + дифф (если есть).
