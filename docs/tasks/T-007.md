ID: T-007
Цель: Настроить Google OAuth и ключи SECRET_KEY/ENCRYPTION_KEY для контейнерной топологии (один origin `http://localhost:8080`).

Контекст:
- Среда: Windows, PowerShell (без `&&`, `export`, `grep`; для поиска `Select-String`).
- Поток OAuth (установлен в T-013): `SetupPage.tsx` делает GET `/auth/google/url`, backend возвращает ссылку Google, браузер уходит на Google. Google возвращает браузер на `redirect_uri`, это **маршрут фронтенда** `/google-callback` (`App.tsx:145`). `GoogleCallback.tsx` читает `code` и делает POST `/auth/google/callback` с `{code}` и JWT. Backend обменивает код на токены и сохраняет refresh-токен в БД.
- Следствие: `redirect_uri` это URL страницы фронтенда. В контейнерах `http://localhost:8080/google-callback`, при разработке на хосте `http://localhost:5173/google-callback`. Значение должно быть одним и тем же в трёх местах: в ссылке авторизации, при обмене кода на токены и в Google Cloud Console.
- В `docs/recon.md` п.8 указано `http://localhost:8000/auth/google/callback`. Для такого потока это значение неверно. Нужно найти, откуда оно взялось (дефолт в коде, `.env`, комментарий).
- Где что лежит: `GOOGLE_REDIRECT_URI` читается в `backend/app/routers/google_auth.py:17-20`, обработчик callback в `google_auth.py:45-67`, `SECRET_KEY` в `backend/app/auth_utils.py:10-15`, `ENCRYPTION_KEY` в `backend/app/core/security.py:17-29`.
- CORS не меняем: в контейнерах один origin.

Файлы (читать можно любые, менять не более 3):
- `backend/app/routers/google_auth.py`
- `backend/app/core/security.py`
- `backend/app/auth_utils.py`

Делать:
1. Описать в ответе, где `redirect_uri` используется в `google_auth.py` (создание ссылки, обмен кода) и откуда берётся значение. Убедиться, что в обоих местах одно и то же значение из `GOOGLE_REDIRECT_URI`. Если значения берутся из разных источников, привести к одному.
2. Если у `GOOGLE_REDIRECT_URI` есть дефолт, не совпадающий с маршрутом фронтенда `/google-callback` (например, `http://localhost:8000/auth/google/callback`), заменить его на `http://localhost:5173/google-callback`. В `.env` контейнера значение задаётся явно.
3. Проверить, делает ли backend где-либо редирект на фронтенд по захардкоженному URL (`RedirectResponse`, `localhost:5173`). Если нет, ничего не добавлять. Если да, вынести в env `FRONTEND_URL` (дефолт `http://localhost:5173`).
4. Проверить, что происходит при незаданных `SECRET_KEY` и `ENCRYPTION_KEY` (дефолт, случайная генерация при старте, ошибка). Если дефолт или генерация, заменить на падение при старте с сообщением, какой переменной нет. Причина: случайный ключ на каждый старт делает зашифрованные в БД данные нечитаемыми после рестарта контейнера.
5. Если для п.1–4 нужно менять больше 3 файлов, остановиться и вернуть список Bridge.

Не трогать: логику OAuth кроме перечисленного, алгоритм шифрования, JWT, модели, CORS, отладочный `print` в `main.py:21`, фронтенд.

Готово, когда:
- в ответе есть описание использования `redirect_uri` (файл:строка) и происхождения значения из recon п.8;
- ссылка авторизации и обмен кода используют одно значение `GOOGLE_REDIRECT_URI`;
- без `SECRET_KEY`/`ENCRYPTION_KEY` приложение не стартует и называет переменную;
- дифф ≤3 файлов, без новых зависимостей.

Как проверить: после T-006 в `.env` задать `GOOGLE_REDIRECT_URI=http://localhost:8080/google-callback`, пройти полную Google-авторизацию на `http://localhost:8080`, выполнить `docker compose restart backend` и убедиться, что вход и загрузка расписания из ЭИОС (расшифровка сохранённого пароля) работают. Для проверки п.4 запустить backend без `ENCRYPTION_KEY` и убедиться в сообщении об ошибке.

Формат ответа: описание использования `redirect_uri` + дифф + список env-переменных для `.env.example`.
