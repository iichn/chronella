# DECISIONS

Формат: ID — решение — причина — статус (`принято` | `предложено`, ждёт Lead).

## D-001 Предмет курсовой — развёртывание
Прикладная логика Chronella не меняется. Правки кода только такие, без которых система не работает в контейнерах.
Статус: принято.

## D-002 СУБД: PostgreSQL 16 вместо SQLite
Отдельный контейнер `db`, данные в томе `pgdata`, доступ только у `backend`.
Статус: принято.

## D-003 Топология
Три контейнера в сети `chronella_net` (bridge). На хост опубликован только `8080:80` (Nginx). Сервисы обращаются друг к другу по именам `db`, `backend`, `frontend`.
Статус: принято.

## D-004 Конфигурация через env
Всё окружение-зависимое читается из переменных окружения. Реальный `.env` в `.gitignore`, в репозитории `.env.example`.
Статус: принято.

## D-005 Схема БД без миграций
Таблицы создаёт `Base.metadata.create_all()` при старте (уже есть в `backend/main.py:15-19`). Alembic не вводим.
Статус: принято (подтверждено T-001).

## D-006 Данные из `database.db` не переносим
Postgres стартует пустым, проект разворачивается с нуля.
Статус: принято (Lead).

## D-007 Google: без файлов credentials
По T-001 файлов credentials/token нет: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` читаются из env, refresh-токены хранятся в БД. Volumes под Google не нужны.
Статус: принято (следует из recon).

## D-008 CI/CD, миграции, мониторинг вне scope
Статус: предложено.

## D-009 Порядок разработки
Сначала Postgres в Docker и приложение на хосте (проверка PG отдельно), затем контейнеризация.
Статус: предложено.

## D-010 Версии
Python 3.12 (как в плане курсовой), Node 22 LTS. В проекте не зафиксированы, фиксируем в Dockerfile'ах.
Статус: предложено.

## D-011 `backend/migrate_db.py` не трогаем
SQLite-only одноразовый скрипт, приложением не вызывается. В контейнерной системе не используется.
Статус: предложено.

## D-012 CORS не меняем, API на фронте через `/api`
В контейнерах браузер работает с одним origin (`localhost:8080`), CORS не задействован. Фронтенд берёт базовый URL из `VITE_API_BASE_URL`, по умолчанию `/api`. Для разработки на хосте: `VITE_API_BASE_URL=http://localhost:8000` (origin `:5173` уже разрешён в CORS).
Статус: предложено.

## D-013 `verify=False` в клиентах ЭИОС не исправляем
Известный риск (`routers/performance.py`, `routers/schedule.py`). Вне scope. Упомянуть в отчёте как найденный долг.
Статус: предложено.

## D-014 Google redirect URI: маршрут фронтенда
По T-013: Google возвращает браузер на страницу фронтенда `/google-callback` (`App.tsx:145`), она читает `code` и делает POST `/auth/google/callback` на backend. Поэтому `GOOGLE_REDIRECT_URI` в контейнерах: `http://localhost:8080/google-callback`; для разработки на хосте: `http://localhost:5173/google-callback`. Значение `http://localhost:8000/auth/google/callback` из recon п.8 для этого потока неверно (источник уточняет T-007). Оба URI добавляются в Google Cloud Console (L-1).
Статус: предложено, код проверяет T-007.

## D-015 Скрипты и команды: PowerShell
Среда Lead: Windows, PowerShell. Скрипт проверки `scripts/smoke.ps1`, команды в ТЗ и чек-листе для PowerShell. README дублирует bash-аналоги для Linux/macOS.
Статус: предложено.

## D-016 Сборка фронтенда в образе: `vite build` без `tsc -b`
`npm run build` (`tsc -b && vite build`) падает на 7 существующих ошибках типов, которые не связаны с контейнеризацией: `App.tsx` (неиспользуемый импорт), `ProfileDialog.tsx` (неиспользуемый импорт, `group`/`faculty` нет в типе), `GradesPage.tsx` (неиспользуемый импорт), `SchedulePage.tsx` (два `Grid item`, API MUI). Приложение при этом собирается и работает в режиме разработки (там типы не проверяются). В Dockerfile используем `npx vite build`, скрипты `package.json` не меняем. Ошибки фиксируем как технический долг в отчёте. Критерий для T-013/T-014: не появилось новых ошибок сверх базовых 7.
Статус: предложено.
